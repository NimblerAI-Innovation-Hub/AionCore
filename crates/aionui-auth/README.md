# Local password storage

Newly provisioned passwords and deliberate password changes/resets use
`$aionui-bcrypt-sha256-v1$` followed by a bcrypt hash at cost 12. The bcrypt input
is the unpadded standard Base64 encoding of SHA-256 over the complete, unchanged
UTF-8 password. This fixed 43-byte input avoids bcrypt's 72-byte truncation and
embedded NUL ambiguity. Passwords are neither trimmed nor Unicode-normalized.

New-password policy now counts 8–128 Unicode scalar values and retains the existing
case-insensitive local common-password denylist. A maximum of 512 UTF-8 bytes
bounds work before copying, lowercasing, or hashing. Login applies only the
maximum, so existing short or common credentials remain usable. Password
verification stays on blocking workers and preserves its minimum response delay;
this change does not add a new global concurrency/rate-limiting policy.

Bare bcrypt hashes remain supported. They cannot reveal the original password
length or any bytes discarded after byte 72. Successful login never rewrites
such a hash: automatically binding a matching prefix/alias to a new hash could
invalidate the original credential. The existing explicit password-change,
local reset, and CLI provisioning paths replace the stored hash with the new
format. There is no bulk migration, forced reset, or external breach-check call.

**Residual risk:** legacy credentials sharing the first 72 bytes remain
interchangeable until their owner deliberately changes/resets the password.
This is compatibility-safe mitigation, not complete closure of legacy bcrypt
truncation. A rollout must not claim otherwise. After new hashes have been
written, an older runtime cannot verify them; any rollback must retain this
verifier (or restore a separately approved consistent pre-upgrade checkpoint).

Focused verification belongs in `tests/password_tests.rs`, the Unicode boundary
case in `tests/validation_tests.rs`, and the existing password-change plus local
reset flows in `tests/route_tests.rs`. The legacy fixture is generated by raw
bcrypt independently of the new writer. Keep existing session, CSRF, account
provisioning, and token-revocation coverage intact.
